# agent-roster: design

How roster should behave, and why. The code is the truth about how it does it; this file is the truth about what it should do. Where the two disagree, one of them is wrong, and which one is decided case by case: this file changes to match the code, or the code to match this file. It stays at the level of features and the decisions behind them; keys, commands and settings are in the README and `roster --help`. It says nothing about what was before or what may come.

Roster is a small, keyboard-first terminal manager for AI coding-agent sessions, written in Rust. One screen: the sessions on the left with their state, the selected one's screen on the right. Enter takes you into the agent, full screen, where you type to it directly; a back key (Ctrl+Q) brings you back. The agents are the real CLIs (Claude Code, pi, Codex, any other), running on roster's own tmux server.

---

## 1. Requirements

1. **Several agents.** Claude Code, pi and Codex have adapters; any other CLI agent runs as a generic one, tracked by its screen. Tracking can't rely on one agent's hooks.
2. **TUI and CLI parity.** Whatever the TUI does, a command does too, so scripts, and agents themselves, can use roster.
3. **Keyboard-first, no mouse capture**, in the TUI and in roster's tmux.
4. **Keys reach the agent unchanged.** While attached, roster's tmux takes only the back key, in a plain terminal and inside the user's own tmux. So roster's tmux never loads the user's `~/.tmux.conf`: nested inside the user's tmux, its prefix and bindings would take keys meant for the agent.
5. **Read/unread that matches reality**: coming back from a session marks it read, and a turn that ends while you watch counts as seen.
6. **Safe keys.** Nothing destructive, and nothing acting on the agent's behalf, on a single key: actions live in menus, and destructive ones also confirm. Only `y` confirms, so an `Enter` pressed by habit confirms nothing. No quick-approve, no YOLO toggle, no restart with a fresh conversation. Every key of the list and its menus can be rebound or turned off.
7. **The environment is made at every start**, by env files that may run commands, so rotating credentials are fresh each time.
8. **Restarting keeps the conversation**, for agents that can resume, and nothing starts a fresh one silently.
9. **Archiving is recoverable**, and deleting for good is a separate, confirmed step.
10. **Low coupling.** Roster never changes an agent's own config or the user's tmux config: whatever it adds to an agent, it adds for that run, at launch. What it writes lives only in its own XDG directories, and of its own config it writes only what is changed in its settings.
11. **What an agent lacks, roster adds per run, and only that**: pi doesn't report its state, so roster loads an extension of its own into the sessions it starts; Codex gets hooks of its own the same way. Nothing it adds changes how the agent behaves for the user.
12. **Several roster processes at once, without lost work.** The TUI, commands and agents calling roster share one database, and none undoes what another saved meanwhile. One TUI runs at a time: one is enough, and commands run alongside it.
13. **Small scope.** Features come when they're needed.

## 2. Concepts

- **Project**: a name, a directory, defaults for its sessions (agent, model, effort), and a note. Every session belongs to one.
- **Session**: one agent at work in a project: its agent, name, directory, conversation, state, title, model and effort, note.
- **Name**: unique among the project's live sessions, made up as `<agent>-<n>` unless you give one. A given name is often a role (`tester`) reused task after task, so it shows next to the title; a made-up one only stands in for a missing title.
- **Agent**: Claude, pi, Codex, or any other CLI configured by its command. Claude is always offered, pi and Codex once installed, others once configured.
- **Conversation**: what the agent keeps of the exchange, in its own files; roster knows its id and resumes it.
- **State**: working, needs input, idle, stopped; plus unread (§3.3).
- **Archived**: put away with the agent stopped, kept with its conversation and note until restored or deleted for good.
- **Chat**: a session without a project of its own (§3.11).
- **Title**: what the session is about: the agent's, or one of yours, which wins.
- **Note**: free text per session, such as what's left to do in it, and per project, such as what's left to do there.

## 3. Running agents

### 3.1 Processes and tmux
- **One binary**: `roster` alone opens the TUI, its subcommands are the CLI, and agents' hooks call `roster report`. **No daemon**: the agents live on roster's tmux server and their reports go straight into the database, so nothing is lost while no TUI runs.
- **A private tmux server** (tmux 3.2 or later), one tmux session per roster session, so they never show in the user's own tmux. Its config is roster's own: no prefix, no bindings but the back key, mouse off, keys passed on as the agents ask for them. It never loads the user's `~/.tmux.conf`; a `tmux.conf` in roster's config directory adds to it, and a prefix or copy mode go there if wanted. It starts without the variables that tie a process to another tmux or to a Claude Code session, so nothing in it takes itself for being inside either.
- A changed config reaches a running server: whenever a roster process starts, and at once for a change of roster's own settings in a running TUI. A mistake in the user's `tmux.conf` is said once, whether a running server reloads the file or a server starts with it, by the next roster you run (roster's own helpers in the background leave it to that one), and roster goes on without it. Saying it again would mean running the file again, which adds twice what it adds; the file is read again once it changes, or when roster's back key or status line changes, which takes reading the whole config again.
- **Attaching** is a plain `tmux attach`: no pty in between and no key filtering, since the back key is a tmux binding. Nothing flashes between roster's screen and the agent's.
- **A status line while attached** shows the project, name, title, agent, model and effort, and the back key. It's set as you attach, so it leaves out the state, which changes while you're there, and a title the agent picks meanwhile shows from the next attach. Why: attached, nothing said which project or task you were in. It can be turned off.
- **Size**: a session is created at the terminal's size, so its output isn't wrapped at 80×24 before the first attach.
- **Agents drawing full screen are fitted to the preview** while no one is attached, so the preview shows all of their screen. Only those: agents on the normal screen garbled scrolling back through their history after a resize. It can be turned off, for programs that redraw badly and for taste: a fitted preview's layout differs from the attached screen's. A resize's redraw isn't taken for activity.
- **Scrolling back and copying** happen in roster's tmux, which has the agent's history; the outer terminal has only the current screen. Copy mode is the user's to add, and the examples show how, including forwarding the user's own tmux's copy-mode key into roster's.
- **Stopped**: the pane outlives the agent, keeping its last screen and exit status. A session whose tmux session is gone (after a reboot) is stopped too.

### 3.2 Launching
- Every start, restart included, runs the whole launch: a POSIX shell (the user's, if it is one; not login, not interactive, so no rc files) sources the global env file, then the project's (`.agent-roster.env` in its directory), then runs the agent. Values are exported, and a failing command stops the start (unless an `export` in front hides its failure): its error stays on the screen and the session shows stopped. A running agent keeps the environment it started with, so credentials that expire mid-session need a helper the agent calls itself.
- Roster picks the session's id, and for agents that take one the conversation's, up front. Codex takes none: it names its conversation, and reports it from its first turn on. The session's identity and roster's own path reach the agent through its environment, so its hooks can report.
- Arguments: the configured ones, then the session's model and effort, so the session wins, then what the adapter needs.
- **Claude** gets roster's hooks through `--settings` for that run, alongside the user's and the project's, and resumes its conversation once there is one. **pi** gets roster's extension through `-e` for that run. **Codex** gets roster's hooks as `-c` arguments for that run, alongside the user's and the project's, and resumes its conversation by id once it has reported one. It runs without its shared server, so its tools get the session's environment, the env files' included, rather than the server's.

### 3.3 State
| State | Meaning | From |
|---|---|---|
| **working** | in a turn | the agent's reports; else its screen changing |
| **needs input** | waiting for you mid-turn (a permission, a question) | the agent's reports; agents that can't report it show idle |
| **idle** | the turn is over, waiting for a prompt | the agent's reports; else its screen still |
| **stopped** | no agent running, for whatever reason | tmux |

- **Reports first, the screen second.** An agent with an adapter reports a turn's start and end, a question, its conversation and model; its screen only corrects an end that went unreported. A generic agent is tracked by its screen alone: changing means working, still for a few seconds means idle.
- **Esc fires no hook**, so a reporting agent that's working, with no new report and its screen unchanged for 4 s, turns idle, and not unread: you interrupted it yourself. This is reliable for Claude, whose spinner changes the screen as long as it works. Codex fires a hook of its own for it (`Interrupt`), which roster doesn't take, so its interrupted turn ends the same way; a turn of its that fails fires none at all.
- **A compaction isn't a start.** Claude and Codex report a compacted conversation as they report a start, often mid-turn when the context is full; it leaves the state as it was, and counts no turn.
- **A subagent's reports are of its parent's turn.** Claude and Codex fire their hooks inside a subagent too, marking them with its id (Codex's name the subagent's own file and model): roster takes nothing of them for the session, and no turn starts from them, even after the parent's turn has ended. Its question counts, as needing your input, until that subagent goes on; one the session asks itself no subagent clears.
- **Subagents left at work keep the session working.** A turn of Claude's own that ends while subagents it started run on (in the background) leaves the session working, not waiting for you and not unread: Claude takes their results up itself as they come. It's idle, and unread, once the last one says it stopped; Claude then reads their results in a turn of its own, working again. Its screen, still meanwhile, is no sign of the end. A question one asks waits on you as any subagent's does, and goes when it stops. One whose start's report was lost (hooks give up when roster's database stays busy for seconds) counts from its first report on, and one whose stop's was (or a session started before roster took them) stops when Claude marks it finished, in its meta file, written since it was last heard of (a mark left from a run it was taken up again after doesn't count). Its card says how many are at work. One that never says it stopped (killed) is taken for gone after fifteen minutes unheard of (past the ten a tool call of Claude's may take), by whichever roster notices first; all are once Claude exits or starts again, and a turn interrupted with Esc, which the screen ends, ends those it ran too. Codex has the same two hooks, which roster doesn't take yet; pi's subagents run within a tool call, so its turn waits for them itself.
- **Unread** is set when a session turns idle or needs input, and cleared when you come back from it, when you start or restore it, or by hand. Looking at the preview doesn't clear it.
- Claude's `Notification` hook isn't used for needs input: it comes about 6 s after the permission prompt, maybe after it was answered.
- On its first start in a directory, Claude asks whether to trust it before any hook fires, so the session shows working, then idle once its screen is still. Codex reports nothing before its first turn, so until then it's tracked the same way.
- **The reporter never fails**: it's silent and exits 0 even when the database is locked or broken, since for Claude a hook exiting with 2 means "keep going". An event it can't store is dropped; a missed end of a turn is caught from the screen.

### 3.4 First prompt
- A new session can get a first prompt, typed into the agent once it's ready: for an agent that reports, once it's idle and has reported its conversation; for others, once its screen is still.
- **Typed as a bracketed paste, a pause, then Enter**: typed as keys with Enter straight after, Claude didn't submit a long prompt. **Not on Claude's command line**: a one-word prompt would run a subcommand.
- **Codex gets it on its command line** instead: it reports nothing before its first turn, so it never says it's ready, and what it may show first takes typed keys (a folder to trust, roster's hooks to review, an update, which Enter installs). On its command line the prompt waits for those to be answered, then starts its first turn; it gets there through a file, so it can be longer than tmux takes a command line, though not than the 128 KB Linux gives one argument: a longer one is refused as the session is made, or started, and stays. Until Codex reports its first turn, the prompt is kept: if it exits first (its trust or update screen declined), the next start goes without it, and the session says so; it's given again only when asked, since Codex may have taken it unseen (its hooks not trusted), and given twice it would act twice.
- **Typed once**, by whichever roster process gets to it. One that couldn't be pasted is tried again a few times, then left to another roster process or the next start; one pasted whose Enter failed isn't, since typing it twice is worse. Failures are said. While you're attached nothing refreshes, so a hidden roster process types it.

### 3.5 Start, stop, archive, delete
- **Start** and **restart** run the whole launch; an agent that resumes goes on with its conversation. For agents that can't resume (generic ones), and for a session whose conversation roster doesn't know (Codex names it from its first turn on, through hooks that may not run), roster asks before starting a new conversation.
- **Stop** ends the agent (SIGTERM, then SIGKILL); the pane stays, with its last screen. Stopping or restarting a working session asks first, since both cut its turn short.
- **Archive** stops the agent, closes its tmux session and puts the session on the Archived shelf, with its conversation and note. **Restore** brings it back stopped (if its name was taken meanwhile, you give it another); starting it then resumes. An archived session's note can still be read and edited; nothing else acts on it.
- **Delete for good**, for archived sessions only, confirmed: the session, its events and its note go. The conversation stays where the agent keeps it, and can be adopted again.
- **Removing a project** needs it to have no live sessions, and deletes its archived ones for good and its note, so it asks first, saying how many and whether it has a note.
- After a reboot every session is stopped; starting one resumes it.

### 3.6 Model and effort
- Per session. A new session takes its own, else its project's (if the project runs the same agent), else the agent's from the config, else none, leaving it to the agent's own settings. "Default", wherever it's chosen, is the agent's from the config, else the agent's own. Changes apply on the next start. Generic agents take neither.
- **What shows is what the agent runs with**: what it reported, else what its start asked for, so an edit shows from the next start.
- **Roster learns what each alias and "default" turned out to be** (`opus · Opus 5.5`), only from the agent's own start, with what that start asked for: not from a conversation cleared or resumed inside it, which may have switched model meanwhile, and not from the session's model as it is now, which an edit may have changed since.
- **Forms offer the agent's models**: Claude's from roster's own list, since Claude can't list its own; pi's and Codex's from the agent, asked in the background. Any other name can be typed.

### 3.7 Titles
- **The agent's own** (Claude's terminal title, pi's session name, the name Codex gives a conversation from its first prompt, in its index of them), or **one of yours**, which wins; taking yours off follows the agent's again.
- **Generated on request**: the session's own agent, run one-off with no tools (or the fewest it allows, none of them able to act) and nothing kept, names what its recent prompts are about. It's kept as your title, since Claude would overwrite its own. It's made in the background, and kept only if the session is still as it was when asked: the same conversation, and no title of yours given or taken off meanwhile. Generic agents can't get one, as roster can't read their conversations.
- **Automatic**, for agents that don't name their task (pi): once per conversation, after its first turn, made the same way and kept as the agent's title, so the agent's own naming still replaces it. One that fails isn't tried again by itself. It can be turned off.

### 3.8 Notes
- Free text per session, kept through stops, restarts and archiving, gone only with the session; and per project, gone only with the project. Why both: a session's note ends with its task, a project's outlives every session in it. Cards mark sessions with one (`✎`); a project with one is marked (`▤`) after its name wherever that shows: on cards, rows, headings and in the projects view.
- **The preview shows them side by side** above the agent's screen, in a faint box from the row under the statistics: the project's pinned lines on the left, the session's on the right, each by its mark, a line between them, so two notes take the rows of one. Stacked one above the other, they took twice the rows and read as one list; without a box, they read as part of the agent's screen. Where the preview is too narrow for two, they're stacked, the project's on top, with a line across the box between them. A note that isn't there takes no room, and one alone has the whole width. A note the preview shows whole (a stopped session's, in its panel) isn't repeated there.
- **Edited inside roster**, under the preview's header with the agent's screen still below, in an editor with vim's keys (operators with any motion, counts and text objects among them, though not `;` and `,`, `~`, `gJ`, `>` and `<`, nor `.` in visual mode); or in `$EDITOR`. `Esc` doesn't close it, so pressing it once too often is harmless. The editor is edtui's, its source in roster (`vendor/edtui`) and patched there where it wasn't vim's or lacked what roster needed; what's changed is listed beside it, so it can be offered upstream.
- **The pin**: the pinned line and the one below it show above the agent's screen, so a to-do list shows where you are in it. How many lines show is a setting, from 1 to 10: more push the agent's screen down.
- **Both open at once**: the editor holds the session's note and its project's as vim holds buffers, `[` showing the project's and `]` the session's, as the preview has them left and right, each keeping its changes while the other shows. The pinned line is marked by the note's own mark, `▤` or `✎`, in the editor as in the preview. `:wa`, `:qa`, `:wqa`, `:xa` act on both; `:q`, `:wq`, `:x`, `ZZ` and `ZQ` close the editor, and refuse while the other has unsaved changes, as vim does with a hidden buffer (`:wq`, `:x` and `ZZ` save the shown one first, as vim writes it). The two yank into one register and repeat one `.`, as vim's buffers do. Opened on a project, only the project's is there.
- **A note changed meanwhile isn't saved over** (an agent ticking a box through `roster note`, say): the save is refused unless you force it, and what you wrote in `$EDITOR` is kept in its file.

### 3.9 Statistics
- For every agent, the session's age, the time spent working, and its turns, or its prompts for an agent whose conversation roster reads. Such an agent adds what its conversation holds: context used of its window, output tokens (its subagents' too: Claude's from their own files, pi's from the tool's result they're kept in), cost, lines changed. A fork counts what it spent itself: the copy of the conversation it came from is in its context, and in none of the rest (Claude's /branch marks the copied lines forkedFrom; a copy roster made, with --fork-session, has them unmarked, with their uuids, which the conversation's own file has, and carries that conversation's cost and lines over, so its own are what it adds to the conversation's last cost-state before the copy; without that file, the copy's lines are those dated before the session, and its cost and lines are left out; codex's copy runs from that conversation's session_meta to the fork's first turn; pi's entries are dated before the fork's header). What's unknown is left out, not guessed. Shown under the preview's header, for archived sessions too.
- The conversation is read incrementally, and the first read must be quick: an 80 MB Claude transcript is normal.

### 3.10 Adopting conversations
- Taking over a Claude, pi or Codex conversation started outside roster (plain `claude`, `pi` or `codex`, an IDE, another session manager), so it goes on as a session here. They're picked from the agents' own files, newest first, with a search: those in your projects' directories, or all of them.
- **Move** (the default): into the project holding its directory, else a new project for that directory; the session runs there and resumes it. **Copy**: a fork, leaving the original untouched.
- **Open elsewhere**: a running Claude leaves a sign, and moving its conversation asks first, since two agents would write one conversation; a copy doesn't. pi and Codex leave none roster can read, so roster can't warn.
- Model and effort: what it last ran with, the defaults, or ones you pick.
- Conversations of live sessions aren't offered; an archived session's is, for restoring.

### 3.11 Chats
- A session without a project of its own, to just talk to an agent. A session still needs a directory (it decides where the agent keeps its conversation, which instructions it reads, where its tools act, which folder it asks you to trust), defaults and an address, which is what a project is. So chats belong to a **built-in chats project**, made on first use, which can be renamed and given defaults.
- **One directory for all chats**, in roster's state directory unless configured: one directory means trusting it once, and uninstalling stays "remove both directories".

### 3.12 Usage
- **What the agents' accounts have used of their limits**: for each window (five hours, a week), how much is left and when it starts over. What's left rather than what's used: it's what you work with, running down as you use it, as a battery does. Claude and Codex say; pi and generic agents don't, and don't show.
- **Asked of each agent itself**, so it shows with no session running: Claude, started in its SDK mode with nothing to do, answering what its `/usage` shows, its own login read by it alone (without `ANTHROPIC_API_KEY`, which Claude takes over its login there, where its sessions take it only if told to; and ended by its input ending, for it to tidy up as it exits); or, as Claude's `limits` setting says, Claude.ai's usage service, as Claude's `/usage` asks it, with Claude's login (roster reads the login Claude keeps and sends its token to an endpoint that isn't documented); Codex's own server, started for it, with Codex's. Each as the agent's sessions would: in the environment they get, so an env file pointing an agent at another account points its usage there too. The env file is sourced once for all of them each time: they're asked every few minutes, and an env file may ask a password manager. Read by roster (`service`), Claude's login is never renewed: renewing replaces what Claude keeps to renew it, which could log Claude out, so an expired login waits for Claude to renew it, and roster says so. The token goes to curl on its stdin, not its command line, where any process could read it. An agent with no login to such an account (Claude on an API key) shows nothing; one that can't be asked says why, keeping what it said before.
- **Codex also writes it into its rollouts** with every response, so a running Codex session's rollout, read whenever it changes, keeps it current between asks for nothing. It holds as of when Codex wrote it, not of the file's last change: Codex writes much else after, and an old figure taken for a new one would undo a newer answer.
- **When**: at the start, every 5 minutes while it shows, and when the view opens, unless just asked; on request too. In the background, so the TUI never waits on a service. What's older than 15 minutes says when it's from, and has no pace.
- **Never, if turned off** (`account_limits`): no agent started, no login read, nothing sent, no server started, by the TUI or `roster usage`, which say how to turn it back on. On by default, being what the view and the sidebar are for; said plainly where it's described, being a login read and sent elsewhere.
- **How it's going**, not only how much: each window is used slower than its time goes by (`▼`, more could be used before it starts over), about as fast (`◆`, within 5 points of its time: five hours' 15 minutes, a week's 8 hours), or faster (`▲`, at this rate it runs out first), or it's used up (`✕`, from where what's left shows as 0%, rounded down). Its bar, what's left and the mark show in its pace's colour: blue, grey, red (used up too, its mark telling it from fast), saturated and blue against red so they're told apart with deuteranopia (asked for by a colour-blind user). A window that has started over since, or doesn't say when it does, or was known long ago, has no pace. Marks rather than words in the sidebar, where words don't fit; words beside them in the view and `roster usage`, and no comment on what it comes to at this rate.

### 3.13 Spent
- **What the agents spent**: tokens of each kind (input beyond the cache, read from the cache, written to it, output) and what they cost at the API's prices, in the last 24 hours, 7, 30 or 90 days: in all, by agent (with how many conversations, and a chart of when), by model. Everything on the machine counts, started in roster or not: it's for knowing how much was used, not where.
- **Read from the agents' own conversations**, call by call, as each records them: Claude's transcripts and its subagents', Codex's rollouts, archived ones too, pi's session files, every branch, with what a tool's result says the tool spent (an extension's own model calls), else the replies pi's subagent extension keeps there (its subagents have no files of their own). Each call counts in the period it was made in, not its file's: a conversation resumed today holds calls from months ago.
- **Kept in roster's database**, call by call: tokens of each kind, cost, and what the cache saved, about 106 bytes a call (its file and model by number, the call by a 64-bit hash of its id, of which two calls sharing one drops the second: of ten million calls, a chance in hundreds of thousands). A database from before that is updated once, as roster first opens it: a few seconds for a million calls, while hooks can't write (a report then is lost, as it is when roster's database can't be written), said on the terminal, the file taking up to twice its room meanwhile and giving the rest back after, in pieces with pauses for hooks to write between, its write-ahead log too (which would otherwise keep that room while any roster has it open). The agents delete their conversations (Claude after 30 days unless told otherwise; you, removing them), and what was spent stays. Kept with the file's modification time and size, so a file unchanged isn't read again, and one that changed is read and saved in place of what was. Each file is read again when what changes reading or prices does (a version saved with each), so a mended reader or a new price reaches all that's still there, and a first reading stopped halfway goes on where it stopped; what's gone keeps what it was saved with.
- **A call counts once, wherever it's copied.** Each is kept by its id as its agent names it (Claude's message, codex's response, pi's entry and its time), by that id's hash, so a fork's copy of the conversation it was forked from (all three agents copy it into the new file, and codex's subagents are forks of their parent) adds nothing; a copy belongs to the file it was read from first. Codex dates its copies as it makes them and names its older calls nothing, so a fork's copy, from its own `session_meta` on, is told by its turns, older than the fork (one that can't be dated is the copy's); an older fork has no copy. A file gone from where it was saved and found by its name elsewhere, of the same conversation (codex archiving a rollout), was moved: it's kept where it is. Another of the same name (a subagent's, of another conversation) isn't it.
- **Cost from a table of the API's prices** in roster, per model, from pi's catalog, with the rates for long calls where a model has them, and Claude's hour-long cache writes at twice input's price. A Claude call is priced as Claude prices it: in fast mode at the Opus model's fast rates, run in the US only at a tenth more, each web search a cent on top. What pi says a call cost counts as said. A subscription's figure is what it would have cost on the API. Models without a known price say so and stay out of the cost, rather than guessed. config.toml can price a model (`[prices]`): one the table lacks, or in the table's place; a change reprices every file still there, as a table's does, and what's gone keeps the cost it was saved with.
- **Read in the background** while it shows, and summed there, so the TUI shows what's saved at once and never waits; a file that changed in the last hour is read only as far as it has grown, and summed again only once something was saved. Saved many files at a time, each read in pieces, so the first read of everything (thousands of files, hundreds of MB) takes about a second and little memory.

## 4. Storage
- **Config** in `$XDG_CONFIG_HOME/agent-roster/`, all optional: `config.toml`, the global env file, the user's `tmux.conf`. An unknown setting is an error, so a setting added later stops an older build instead of being ignored. Changes on disk are used at once.
- **Roster writes `config.toml` only for a change made in its settings**, and only that setting (taking one out takes its comment with it): the rest of the file stays as written, comments included; what was edited outside meanwhile is kept; and a symlinked file stays where it points. The one other write is the template, when you ask to edit a file that isn't there. Why: the settings should configure everything, and a config kept in git shows what changed.
- **State** in `$XDG_STATE_HOME/agent-roster/`: the database (SQLite, also keeping what the agents spent, §3.13), the files roster makes for itself (the generated tmux config, pi's extension, notes being edited, the TUI's lock), and the chats' directory. An older database is migrated when opened; a newer one is refused.
- **Uninstalling**: the binary, both directories, and roster's tmux server.
- **Several processes**: reports are stored as events, which every roster process folds into sessions; roster's own changes fold pending events first, so an older event can't undo them. A save writes only what it changed, so nothing reverts what another process saved meanwhile. Where you and a process may both write the same thing (a note, a generated title), the write happens only if it's still what it was. A removed project's id is never given to another, so what was opened on it (its note, in an editor) can't be saved onto a project added since.

## 5. TUI
- **Layout**: a narrow sidebar with a summary of what waits ("2 need input · 1 working"), the list, and, once known, a line with what's left of the agents' accounts' limits (each agent's windows, shortest first, each with its pace's mark, by the agent's mark where names don't fit, then only each agent's shortest, never a figure cut short; it can be turned off); the preview on the right; the footer below. No boxes around them, only a line between them; popups, forms and the note editor are boxed.
- **Shelves, by attention** (the default): at the top what waits for you (Needs input: questions, permissions and finished turns you haven't read; Idle; Stopped), at the bottom what's handed off or finished (Working, then Archived, folded). Why: working is "go away, I gave it a task", stopped is idle without a running agent, archived is finished. Grouping by project is the alternative, a setting: it's how you keep the list, not something flipped for a look (showing only one project is), and a key for it was lost on every restart.
- **Within a shelf, first come, first served**: oldest first, so a card you're reading isn't pushed down by newcomers; in Needs input, questions and permissions come first. Reports that don't change a session's state don't move it. Each shelf's order can be changed, being a matter of taste.
- **The cursor follows its session**, except when you come back from giving it a task: then it keeps its row, landing on what took the session's place, usually the next one waiting. Why: answering an agent sent its card, and the cursor with it, to the bottom; going by whether the card changed shelf would also jump after only reading. Lists wrap around.
- **Cards**: the project, as a coloured badge and its name in that colour, since the badge alone didn't tell projects apart; the title and the state; the agent, name, model and effort. Stopped and archived sessions are one-line rows.
- **A card's subagents at work** are counted on its second line, and the card unfolds, as a shelf does, to a line for each: the model it runs, what it's doing (cut to fit: the list is narrow), how long it's been at it. What it's doing is its latest tool call in a few words, as Claude's footer says it (a command's own description, the file it reads or edits, the todo at work); Claude writes the footer's line nowhere, so it's made from the subagent's transcript, read from its end at each refresh. Till its first call, what it was given to do stands in. Folded by default, as lines coming and going move the list; unfolded always, or the count only, as set. The model is the one its replies are from, else, till it replies, the one it was asked to run on (its parent's, the session's, if it inherits). What it is is read for unfolded cards only, and for a couple of minutes at most after it starts, while its files are written. Its own screen, the agent's footer, says the rest.
- **The preview**: a header (project, name, title, agent, model, effort, state) and the statistics, then the live session's screen, read-only. Lines too wide are cut, not wrapped: wrapping breaks agents' box drawing. A stopped or archived session shows a panel of what it was and what starting it goes on with, including the end of its screen after an exit with an error, where an env file's error is. A heading shows its sessions at a glance. No key hints in a session's preview: they only repeated the footer and the menus. Where nothing else says what can be done (nothing to select, a project's details), the preview says it.
- **Filter**: `/` narrows the list fuzzily, fzf-style, keeping the shelves. The summary at the top still counts every session, so nothing waiting is missed.
- **Views**: the projects; the tmux server and database (§7); the settings, where every setting shows with what it does and changes apply at once (prices aside: a table of numbers per model, edited in the file); usage (§3.12), each window a bar of what's left, full while none is used, with a mark where as much of its time is left, so a bar ending short of the mark is used faster than the window lasts, and in tabs beside it what was spent in each period (§3.13). In a view, `q` goes back, since quitting from a view surprised.
- **The footer** shows the keys that act where you are, with messages beside them rather than over them. Help shows the keys of the list and its menus.
- **Keys**: vim-style moving at the top level; the list's actions in three menus (session, project, view), where a letter means the same in each (`n` new, `e` edit, `d` archive or remove). The back key must be one an agent rarely needs: with Ctrl or Alt, or an F key, and not one a terminal sends for something else (Ctrl+M is Enter, Ctrl+I Tab).

## 6. CLI
- Every TUI action has a command (§1.2), and `roster ls --json` is for scripts.
- The CLI asks where the TUI asks; `--yes` answers for scripts and agents, and without a terminal it refuses rather than guess. Where the TUI offers something else instead (another name for a restore, restoring an archived session rather than adopting its conversation), the CLI says what to run.
- A session is addressed by its id, `project/name`, its name, or an id prefix; an address that fits several is an error.
- A few commands are roster's own: the hooks' reports, typing a first prompt while you're attached, automatic titles. A log of reports is for debugging.

## 7. Diagnostics
- `roster doctor` and the server view check roster's tmux server and the database against each other: whether the server runs roster's config and was started clean (no other tmux's or Claude Code's variables), each tmux session against its roster session, and the database's state. The problems are a server without roster's config, a server not started clean, and orphans (tmux sessions no live roster session owns), which can be killed after asking. `roster doctor` exits with 1 while problems remain.

## 8. Left out on purpose
- **Telling an answered permission prompt.** Claude has no hook for an approval, so a session stays in Needs input until the approved tool finishes. Most people run agents in auto mode, and recognising Claude's dialog on its screen isn't worth it.
- **Jumping to the next waiting session while attached.** The list in between is the loop: attached, you don't see what's next.
- **A live side panel** (the agent's pane beside the TUI): `join-pane` works only within one tmux server, and the TUI isn't on roster's. Fitting agents to the preview does it instead.
- **Ignoring parts of a generic agent's screen**: all of it counts, so an agent that redraws while idle (a clock) flips between working and idle.
- **tmux control mode or file watching**: polling once a second is enough.
- **Usage over time**: what an account used shows as it is now; keeping it to draw its history isn't worth it. What was spent is kept (§3.13): it's what the conversations held, and they go.
- **Prices from a service**, or set in the config: the table in roster follows the models the agents run, and a price unknown shows as unknown.
- **macOS and other systems**: roster runs on Linux.
- **Narrow races, accepted**: a refresh writes the state it observed, so in a narrow window another process's fold can lose to it; a first prompt claimed but not yet typed is lost if roster is killed in between; a resize's redraw may count as activity once for another roster process; a start reported after a quick edit of its model is learned under the edited alias; Codex reports its start with its first turn, so a model switched inside it before the first prompt is learned as what its start asked for.

## Appendix: what roster relies on

Checked against the real programs (tmux 3.5a, Claude Code 2.1.303 and later, pi 1.4.0, Codex 0.163.0 and 0.164.0). A change in one of these can break roster.

**tmux**
- Extended keys and `new-session -e` exist from 3.2.
- `resize-window`, then unsetting `window-size`, keeps the new size until a client attaches, which then sizes the window as usual.
- An attaching client draws through the terminal it opens itself.
- A server that started with mistakes in its config keeps them, and the next `source-file` prints them, once.
- A key the outer tmux binds without a prefix is taken there before it reaches roster, as in any pane.

**Claude Code**
- Hooks given with `--settings` fire alongside the user's and the project's own.
- A prompt is written as a string, or as a list when it has an image or a file; since 2.1.283 a prompt carries `promptSource`, and the other lists (tool results, its markers such as an interruption) don't.
- Every hook payload names the conversation and its transcript; `SessionStart` says whether it started, resumed, cleared or compacted one, and the model only for a new conversation.
- Esc during a turn fires no hook; an approved permission fires none until the tool has run; `Notification` comes about 6 s after a permission prompt.
- Beside each subagent's transcript, `agent-<id>.meta.json`, written as it starts (and again with `finished` as it ends): `agentType`, `description` (its task, in a few words), and `model` when one was asked for (an alias, `sonnet`; `inherit` for a fork; often none). A forked one's transcript begins, before its task, with a copy of the reply it was forked from.
- `SubagentStart` and `SubagentStop` fire as each subagent starts and ends its turn (with `agent_id` and `agent_type`), in the background too, after the session's own `Stop` (2.1.311). Not seen: whether a subagent interrupted with Esc fires `SubagentStop`, and whether the turn Claude takes to read a background subagent's result fires `UserPromptSubmit`.
- `--session-id` fails once the conversation has messages, `--resume` gets it back, and `--fork-session` copies it, written with its first message.
- A one-word prompt on the command line runs a subcommand, `--` notwithstanding; a long prompt typed with Enter straight after isn't submitted, but a bracketed paste, a pause, then Enter is.
- Working, its screen changes at every sample; idle, it stays identical.
- Its terminal title names its task after a glyph (`✳`, or another such as `⠐`) from the first prompt on.
- A running Claude keeps `<claude dir>/sessions/<pid>.json`, removed on exit.
- On its first start in a directory it asks whether to trust the folder, before any hook.
- Its classic renderer draws on the normal screen, where a resize garbles scrolling back; the fullscreen one draws in the alternate screen.
- `--fork-session` copies the conversation into the new transcript as it was, each line with its `uuid`, each reply with its `message.id` and `timestamp`, only `sessionId` changed; no cost-state is copied, but the cost ledger is restored from the conversation's last one, so the copy's cost-states carry its cost, lines, model usage and start time on (2.1.311, seen in a copy's file).
- A transcript writes a reply once for each of its parts (thinking, text, each tool call), with the same `message.id` and its `usage` each time, as of then: `input_tokens` beyond the cache, `cache_read_input_tokens`, `cache_creation_input_tokens` (of which `cache_creation.ephemeral_1h_input_tokens` were kept an hour: all of them, with 2.1.310) and `output_tokens` (any of them may be null), with the line's `timestamp`; `server_tool_use.web_search_requests`, `inference_geo` (`us` for a call run in the US only) and `speed` (`fast`) change its price, which Claude 2.1.311 reckons as `STt` does: fast rates for the Opus models that have them, twice the normal ones (six times for Opus 4.6 and 4.7), the US at 1.1 times, $0.01 a search on top. Its own messages (an error) have the model `<synthetic>`. A subagent's transcript is `<conversation>/subagents/agent-<id>.jsonl` beside the conversation's, or in a directory beneath `subagents/` (`agentRelPath`, as Claude names some), and its calls aren't in the parent's.
- Its login to Claude.ai is in `<claude dir>/.credentials.json` (`claudeAiOauth`: the token, when it expires in ms, the plan as `subscriptionType`); on an API key there's none. Claude renews the token itself.
- `GET https://api.anthropic.com/api/oauth/usage`, with that token and `anthropic-beta: oauth-2025-04-20`, is what its `/usage` asks: `five_hour` and `seven_day`, each `utilization` (a percentage) and `resets_at` (ISO 8601, a moment either side of the minute), with more besides. It's not documented, so it may change; an expired token gets 401.
- In its SDK mode (`claude -p --input-format stream-json --output-format stream-json --verbose`), it answers a `get_usage` control request, after `initialize`, with what its `/usage` shows: `subscription_type`, `rate_limits_available` (false on an API key), and `rate_limits` (`five_hour`, `seven_day`, each `utilization` 0 to 100 and `resets_at`, ISO 8601); `skip_behaviors` skips its scan of the local transcripts. It calls the request experimental. With no prompt it calls no model, and with `--strict-mcp-config --setting-sources ""` it starts no MCP server and reads neither the user's nor projects' settings (managed settings still apply; with a managed MCP config it refuses `--strict-mcp-config`); it exits as its input ends, removing the file it registers its pid in (`sessions/<pid>.json`), which a killed one leaves (2.1.311). There, `ANTHROPIC_API_KEY` is used over the login, unasked. A plan whose figures it couldn't fetch answers `rate_limits_available` true and `rate_limits` null, or the figures it kept from up to an hour before, unmarked.

**pi**
- `-e <file>` loads an extension for that run, alongside the user's own; `--session-id` opens a conversation or creates it; `--fork` copies one; `--list-models --offline` lists its models.
- `agent_end` can be followed by retries; `agent_settled` comes once the turn is really over.
- It leaves no sign that a conversation is open.
- Each reply in its session file has its `provider`, `model` (and `responseModel`, the one that answered, if the provider said), `usage` (`input` beyond the cache, `cacheRead`, `cacheWrite`, `output`) and its `cost` as pi works it out, `total` 0 for a model it knows no price for; model calls outside the conversation are entries of their own with a `usage`: cache warming (`usage`, with its own `provider` and `model`), and the summaries of a `compaction` and a `branch_summary` (with no model). A fork (`--fork`, and a session branched off into its own file) gets a new header, with `parentSession`, and a copy of the entries as they were, their ids and timestamps too.

**Codex**
- It takes no id for a new conversation; it names it, and its hooks report it from its first turn on, `SessionStart` too, saying `startup`, `resume`, `clear` or `fork`, with the model. `resume <id>` gets a conversation back, and says so if it can't find it; `fork <id>` copies one, whose rollout names the one it came from and, since 0.137, begins with a copy of it (below); `debug models` lists its models.
- Esc during a turn fires `Interrupt`, not `Stop`; a turn that fails (the model's error) fires neither.
- At a start it may first ask to trust the folder, or offer an update, which Enter installs.
- It names a conversation from its first prompt, within seconds, keeps the name until it's cleared, and appends it to `session_index.jsonl` (renamed, again); its terminal title shows it too, in a form the user can configure.
- `--no-daemon` runs its tools in its own environment.
- Hooks given with `-c hooks.<Event>=[…]` are a layer of their own and fire alongside the user's and the project's, whether those are in `config.toml` or `hooks.json`, though the merged config shows only the `-c` ones.
- `codex exec` always offers the model `exec` and `request_user_input`, whatever is turned off; with `code_mode_host` off, `exec` fails at once, and in a read-only sandbox `apply_patch` is refused. The user's own `AGENTS.md` comes whatever is turned off; `project_doc_max_bytes=0` keeps out the project's.
- An unknown feature is an error for `--disable`, a warning for `-c features.<name>=false`.
- The trust of hooks given with `-c` is kept per event, for whichever command was trusted last: trusting roster at another path untrusts it at the one before.
- New or changed hooks are reviewed at its start, and a prompt on its command line waits for the answer: trusted, its first turn reports; reviewed one by one or not trusted, it runs without them. Every hook payload names the conversation, so the next turn that reports says it.
- Its rollout gives the model context as user messages too. Since 0.157 it marks each message's parts with their kinds (`user.text` for a prompt); before, it marked none and wrote each prompt again as a `user_message` event, which 0.124 also wrote beside marked messages. A prompt given on its command line is a prompt like any other.
- `codex app-server` answers its JSON-RPC protocol on stdin and stdout, after the `initialize` handshake, until its stdin ends, and stops at once when it does, even with a request unanswered. `account/rateLimits/read` gives the account's limits (`primary`, five hours, and `secondary`, a week: `usedPercent`, `windowDurationMins`, `resetsAt` in seconds; `planType`) and the resets it has granted; without a login to an account it answers an error saying authentication is required.
- Every line of its rollout has its `timestamp` (ISO 8601). Every `token_count` carries the same limits, in snake_case, as `rate_limits` with `limit_id` `codex` (0.120 to 0.164 alike); rarely, another kind of limit's, with another `limit_id`.
- Since 0.163 at the latest its rollout records each model call as a `token_usage_record` (with the `thread_id` it's of and its `response_id`), its `usage` with `input_tokens` counting the cached ones too (`cached_input_tokens`, and `cache_write_input_tokens`, always 0 so far), then the `token_count` after it; before, only the count has them, as `last_token_usage`, written again without a call between (its `total_token_usage` unchanged). The model is the turn's, from its `turn_context`. A resumed conversation goes on in the same rollout, from an older version too, so one rollout can have both.
- A fork's rollout (a subagent's too) begins with its own `session_meta` (with `forked_from_id`), then a copy of the conversation it was forked from, its `session_meta` first, every line dated as the copy was made (0.137). Turn ids are UUIDv7: the copied turns' are older than the fork, its own first one's newer. Archiving moves a rollout, its name unchanged, to `archived_sessions/`.
- Its rollout records each edit with what it changed, by file (added or deleted with the content, updated with a diff): before 0.157 as a `patch_apply_end`, since 0.163 as an `item_completed` of a `FileChange`, never both.
